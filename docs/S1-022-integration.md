# S1-022: Persist Reviews with Target Ownership

## Implemented scope

The review service saves and retrieves reviews using the current
user-owned products model.

Each review document in the root reviews collection contains:
- reviewId: generated by Firestore.
- userId: supplied by the backend from verified identity.
- productId: the owned target's identifier.
- createdAt: a server-generated timestamp.
- Allowlisted review text, rating, and supported metadata.

Existing ownership and normalization helpers are reused. No new
dependencies or configuration changes are required.

## Service interface

```js
import { saveReviews, getReviews } from './services/reviewService.js';

const saved = await saveReviews(uid, productId, acceptedReviews);
// { reviewIds: ['generated-id'], count: 1 }

const reviews = await getReviews(uid, productId);
// Array of stored review records.
```

Adjust relative imports for the caller's location.

Both functions accept an optional final database argument for tests.
Otherwise, they use the configured backend database.

The uid must come from verified req.user.uid when called through an
HTTP endpoint. It must never come from request-body ownership fields.

## Validation and ownership

Both functions validate identity and the product identifier.

The existing getOwnedProduct helper checks ownership before review
database access. Missing products and another user's products return
404 PRODUCT_NOT_FOUND.

Retrieval filters by both userId and productId.

Before saving, records pass through normalization again to validate
required fields and allowlist supported metadata. Incoming ownership,
database IDs, timestamps, and unsupported properties are discarded.

If any record is invalid, the entire save is rejected rather than
silently dropping records.

Empty saves still check product ownership and return:
{ reviewIds: [], count: 0 }

An empty save does not establish successful populated ingestion.

## Atomic writes and limits

Each save accepts at most 400 reviews and uses one atomic write batch.

Larger inputs return 400 VALIDATION_ERROR before writes. They must not
be silently truncated.

A successful result is returned only after the batch commit completes.
Database failures propagate to the caller.

Multi-batch ingestion and lifecycle races involving concurrent target
deletion are outside this implementation.

## Duplicate handling

sourceReviewId is preserved when available so source duplicates can be
identified later.

Each save currently generates new Firestore document IDs. Repeated
imports can therefore create duplicate reviews.

Sophisticated re-ingestion and duplicate resolution are deferred, as
permitted by S1-022.

## Controller integration

Controllers must supply the verified uid and use the standard API
response envelope.

The service returns internal JavaScript results, not HTTP responses.

For the stored-review list endpoint, the response shape follows the
engineering standards:

```json
{
  "data": [],
  "nextCursor": null,
  "count": 0
}
```

Timestamp serialization, pagination and cursor handling remain
integration work. getReviews currently returns all matching records
without guaranteed ordering.

No routes or controllers are added by this service. Database errors
must be sanitized by the application's error middleware.
